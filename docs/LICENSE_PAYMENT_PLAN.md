# QR-оплата + автоактивация лицензии — план внедрения

Коротко на главный вопрос: **да, jsonbin.io после этого больше не нужен.**
Сейчас `license.py` просто дёргает `LICENSE_URL` (jsonbin) и читает оттуда JSON со
статусами. Как только у вас появится свой сервер, который отдаёт тот же
"статус лицензии" — `LICENSE_URL` меняется на ваш адрес, и jsonbin можно
отключать. Он был временной "базой данных для бедных", а не архитектурным
требованием.

## Serverless-вариант (нет своего постоянного сервера)

Полный план ниже (Этапы 1-7) предполагает свой backend на `backend/`
(FastAPI + БД). Если постоянного сервера нет и поднимать его пока не хочется —
есть готовая бессерверная замена в папке `license-worker/` (Cloudflare
Workers, бесплатный тариф): она делает то же самое (создать платёж в ЮKassa,
принять webhook, проставить `active` в jsonbin), но без базы данных и без
хостинга, который нужно администрировать. jsonbin в этом варианте
**остаётся** (роль "базы лицензий" на нём), просто пишет в него теперь не
клиентское приложение напрямую, а воркер — см. `license-worker/README.md`.

## Итоговая карта путей: что открыто, что закрыто

| Путь | Кто дёргает | Защита |
|---|---|---|
| `GET /license/status?key=...` | приложение (при каждом запуске) | публично, **только чтение**, без прав на запись |
| `GET /pay/{checkout_token}` | браузер клиента (после скана QR) | публично, без логина — токен длинный и случайный |
| `POST /webhook/yookassa` | серверы ЮKassa | публично по URL, но подпись/перезапрос статуса обязателен |
| `POST /webhook/am-gateway` | серверы армянского эквайринга | то же самое, свой механизм подписи |
| `POST /admin/licenses`, `GET /admin/licenses` | только вы/друг | закрыто логином (admin JWT), наружу не торчит |

Главный принцип: **приложение на компьютере клиента никогда не получает ключ с правом записи.** Сейчас в `license.py:29-30` зашит `API_KEY` от jsonbin с правом на запись — это и есть дыра, которую новый сервер должен закрыть.

## Этап 1 — Хранилище лицензий на вашем сервере

Добавить в существующий `backend/` (у вас там уже FastAPI + модели) таблицу вида:

```
licenses
  id
  license_key      -- длинный случайный токен, то, что сейчас лежит в license.key у клиента
  checkout_token    -- отдельный случайный токен для ссылки оплаты (не обязателен, но чище: чем меньше мест где "светится" рабочий ключ — тем лучше)
  active            -- bool
  billing_provider  -- 'ru_yookassa' | 'am_gateway' | 'lifetime' | ...
  client_name       -- для вашего удобства, не для логики
  created_at
  activated_at
```

`billing_provider = 'lifetime'` — для клиентов с разовой фиксированной оплатой
("заплатил один раз — пользуется сколько хочет", по договорённости вне
системы). У таких лицензий `active` выставляется вручную один раз и больше
не трогается — вебхуки/автосписания/проверки подписки их не касаются
(в коде вебхуков просто не обрабатывать этот provider).

Это полностью отдельная таблица от базы автосервиса клиента — она живёт только у вас, клиент её не видит.

## Этап 2 — Эндпоинт статуса лицензии (только чтение)

`GET /license/status?key=XXXX` → `{"active": true}` или `{"active": false}`.

Требования:
- Никакого секретного ключа/токена авторизации в самом приложении для этого запроса не нужно — это публичный, но **read-only** путь.
- Добавить rate limit (в `docs/DEPLOY_HTTPS.md` у вас уже описан `slowapi` для `/auth/login` — тот же приём здесь), чтобы никто не перебирал ключи брутфорсом.
- В `license.py`:
  - `LICENSE_URL` → ваш новый адрес.
  - убрать `headers={"X-Access-Key": API_KEY}` и саму переменную `API_KEY` — она была нужна только для jsonbin.
  - `_check_online()` упростится: парсите `{"active": true/false}` напрямую, без обёртки `licenses{...}`.

## Этап 3 — Ссылка оплаты (генерация QR)

`GET /pay/{checkout_token}`:
1. Находит лицензию по `checkout_token`.
2. Смотрит `billing_provider`.
3. Создаёт платёж через нужный SDK:
   - `ru_yookassa` → ЮKassa `Payment.create(...)`, в `metadata` кладёте `license_key`, чтобы потом в вебхуке знать, кого активировать.
   - `am_gateway` → аналогично через API армянского эквайринга (уточните у банка друга формат: обычно тоже "создать платёж → получить ссылку на оплату").
4. Редиректит браузер клиента на полученную страницу оплаты провайдера.

QR на экране логина кодирует **всегда один и тот же вид ссылки** — `https://вашдомен/pay/{checkout_token}` — и генерируется локально библиотекой `qrcode` (она уже используется в проекте), без обращения к сети. В сеть идёт только сам браузер клиента, когда он реально открывает ссылку.

## Этап 4 — Вебхуки провайдеров

`POST /webhook/yookassa`:
- Получили уведомление → **не доверяем телу запроса напрямую**.
- Берём `payment_id` из уведомления → запрашиваем реальный статус через API ЮKassa (`Payment.find_one(payment_id)`).
- Если статус `succeeded` — берём `license_key` из `metadata` этого платежа → `UPDATE licenses SET active = true WHERE license_key = ...`.

`POST /webhook/am-gateway`:
- Та же логика, но с проверкой подписи/статуса по документации конкретного армянского провайдера (у каждого банка свой формат — уточнить в их API-доке).

Оба пути публичны по URL (иначе провайдер не достучится), но эффективно закрыты, потому что подделать подтверждение оплаты, не зная секрета подписи и не имея доступа к API провайдера, нельзя.

---

## Этап 5 — Админка выдачи лицензий

`POST /admin/licenses` (создать лицензию: сгенерировать `license_key` + `checkout_token`, указать `billing_provider`), `GET /admin/licenses` (посмотреть список).

Закрыто обычной авторизацией — у вас в `backend/app/routers/auth.py` уже есть JWT-логин, просто вешаете `Depends(...)` с проверкой роли admin на эти роуты, как на остальные защищённые эндпоинты.

---

## Этап 6 — Обновление десктоп-приложения

- `license.py`: новый `LICENSE_URL`, убрать `API_KEY`/jsonbin-специфичный код (см. Этап 2).
- `login_window.py`: если `check_license()` вернул `False` — показать QR (сгенерированный из `checkout_token`, который лежит в `license_cache.json`/рядом с `license.key`) и кнопку "Я оплатил, проверить снова" → повторный вызов `check_license()`.

---

## Этап 7 — Отключение jsonbin.io

После того как Этап 2 заработал и `license.py` смотрит на ваш сервер:
- `LICENSE_URL` и `API_KEY` в коде больше нигде не используются — можно удалить эти константы.
- Сам бин на jsonbin.io можно удалить/перестать оплачивать — зависимость исчезает полностью.

---

## Порядок, в котором имеет смысл делать

1. Этап 1 (таблица) + Этап 2 (чтение статуса) — переключить `license.py`, убедиться что старые лицензии продолжают работать (перенести текущие ключи из jsonbin в новую таблицу).
2. Только после этого — Этап 3+4 (оплата и вебхуки) для одного провайдера (например, ЮKassa, раз он уже частично освоен в `tgbot/main.py`).
3. Добавить второго провайдera (армянский) — по той же схеме, отдельным адаптером.
4. Этап 5 (админка) и Этап 6 (QR на логине) — когда первый провайдер уже подтверждённо работает end-to-end.
